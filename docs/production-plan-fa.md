# راهنمای آماده‌سازی و انتشار سنگ اصفهان

تاریخ بررسی: ۲۳ اکتبر ۲۰۲۶. دامنه: sangesfahan.com.
این سند برنامهٔ اجرا پس از اجازهٔ مالک است؛ هیچ سرویس، DNS یا دیتابیس زنده‌ای تغییر نکرده است.
گزارش ممیزی و نتیجهٔ واقعی آزمون‌ها در `production-audit-2026-10-23.md` است.

## ۱. چه چیزهایی تهیه شود؟

برای پنج کسب‌وکار، حدود بیست کاربر هم‌زمان و خروجی زیاد:

| سرویس | پیشنهاد شروع | نقش |
|---|---|---|
| برنامهٔ مدیریت‌شدهٔ Docker در ایران | ۴ گیگابایت RAM، دو vCPU | Django، Gunicorn، تولید PDF/PNG |
| PostgreSQL مدیریت‌شده | نسخهٔ ۱۶، حداقل یک گیگابایت RAM و ده گیگابایت دیسک | کاربران، فاکتور، دفتر حساب |
| Redis مدیریت‌شده | کوچک‌ترین پلن، حدود ۵۱۲ مگابایت | محدودیت مشترک تولید خروجی میان پردازش‌ها |
| فضای S3 خصوصی | ابتدا ۲۰ گیگابایت قابل ارتقا؛ برای ویدئو احتمالاً بیشتر | عکس، ویدئو، امضا |
| پشتیبان مستقل | فضای خصوصی جدا با دسترسی محدود | بازیابی دیتابیس و فایل‌ها |
| کاوه‌نگار | پیشرفته برای شروع، سپس بررسی حجم واقعی | کد کارکنان و مشتریان |

این منابع تخمین مهندسی‌اند؛ تحمل بیست تولید هم‌زمان PDF هنوز اندازه‌گیری نشده است.
سه پردازش وب نقطهٔ شروع است. پیش از انتشار، مصرف RAM هنگام خروجی چندصفحه‌ای و
زمان پاسخ با بیست نشست آزمایش شود؛ در صورت نیاز، پردازش خروجی صف‌بندی شود.
برنامه در حال حاضر صف تولید PDF ندارد؛ خرید Celery به‌تنهایی آن را ایجاد نمی‌کند.

در صفحهٔ فعلی [تعرفهٔ لیارا](https://liara.ir/pricing/)، قیمت پایهٔ ماهانهٔ
برنامهٔ زحل ۴٬۱۲۵٬۰۰۰، دیتابیس مریخ ۱٬۳۰۰٬۰۰۰، دیتابیس زمین برای Redis
۷۵۰٬۰۰۰ و فضای ۲۰ گیگابایتی ۴۷۵٬۰۰۰ تومان درج شده است: مجموع پایه حدود
۶٬۶۵۰٬۰۰۰ تومان. این عدد شامل پیامک، امکانات اضافه، فضای بیشتر، پشتیبان مستقل،
مالیات احتمالی یا هزینهٔ ترافیک نیست؛ قیمت نهایی در پنل خرید تأیید شود.
قیمت ترافیک VPS را به PaaS یا S3 تعمیم ندهید. برای ویدئو، سقف و تعرفهٔ دانلود را
جدا استعلام کنید. برای نمونه، ۱۰۰ کلیپ ۳۰ مگابایتی با هزار بار پخش هرکدام
تقریباً سه ترابایت ترافیک ایجاد می‌کنند.

هاست اشتراکی برای این مسیر پیشنهاد نمی‌شود. VPS ارزان‌تر ممکن است هزینهٔ
مدیریت و بازیابی بیشتری داشته باشد. انتخاب فعلی لیارا با PostgreSQL و Redis
در یک شبکهٔ خصوصی است؛ موقعیت ایران و نسخهٔ PostgreSQL را در سفارش تأیید کنید.
Docker فعلی برای کتابخانه‌های Pango و PDF حفظ می‌شود؛ لازم نیست Docker Desktop
را برای مدیریت روزمرهٔ سایت روی رایانه نصب کنید.

## ۲. پیامک کارکنان و مشتریان

[تعرفهٔ کاوه‌نگار](https://kavenegar.com/pricing.html) پلن پیشرفته را سالانه
۶۰۰٬۰۰۰ و فوق‌پیشرفته را سالانه ۱٬۲۰۰٬۰۰۰ تومان اعلام می‌کند. طبق بخش پرسش‌های
همان صفحه، OTP در این دو پلن فعال است و برای بیش از ۵۰۰ پیامک در روز، بررسی
فوق‌پیشرفته پیشنهاد شده است. جدول بالای صفحه دربارهٔ استاندارد مبهم است؛
فعال‌سازی Lookup را پیش از پرداخت از فروش تأیید کنید.

ابتدا حساب آزمایشی بسازید؛ پس از تأیید ارسال، پیشرفته مناسب شروع است.
تعداد مشتری ثبت‌شده معیار خرید نیست: تعداد درخواست کد، ارسال مجدد و پیامک
قابل‌صورتحساب مهم است. هر ۱۰۰ درخواست روزانه تقریباً ۳۰۰۰ ارسال ماهانه است،
بدون احتساب تکرارها. هزینهٔ مصرف جدا از اشتراک است؛ نرخ دقیق Lookup، مالیات،
ظرفیت لحظه‌ای و تعرفهٔ پلن‌ها را از پنل بگیرید. فوق‌پیشرفته وقتی اقتصادی است
که صرفه‌جویی سالانهٔ مصرف از ۶۰۰ هزار تومان اختلاف اشتراک بیشتر شود.

در پنل کاوه‌نگار سرویس اعتبارسنجی و یک الگوی تأییدشده به نام `sanga-otp`
با یک متغیر کد ایجاد کنید. متن پیشنهادی: «کد تأیید سنگ اصفهان: %token».
املای نام قالب در پنل و متغیر محیطی باید یکسان باشد. برنامه از
`verify/lookup` استفاده می‌کند و هم ورود کارکنان و هم تأیید شمارهٔ مشتری
از همین اتصال استفاده می‌کنند؛ تأیید مشتری برای او حساب کاربری نمی‌سازد.
برای Lookup طبق [معرفی رسمی](https://kavenegar.com/sms/verification)
نیازی به تبدیل خط اختصاصی خودتان به خدماتی نیست.
کلید را فقط در متغیرهای محرمانهٔ میزبان قرار دهید.

در محیط آزمایشی با شمارهٔ مجاز خودتان، رسیدن واقعی پیامک، کد غلط، انقضا،
ارسال مجدد و یک شماره با تبلیغات مسدود را امتحان کنید. تست ساختگی API، تحویل
واقعی پیامک را ثابت نمی‌کند. افزایش سقف پیامک فقط پس از بررسی سوءاستفاده باشد.

## ۳. قبل از ساخت برنامه

در لیارا حساب بسازید و احراز هویت را انجام دهید. سرویس‌های برنامه، PostgreSQL
و Redis را در همان شبکهٔ خصوصی بسازید. اطلاعات اتصال را در مدیر رمز عبور
ذخیره کنید. پورت دیتابیس و Redis را عمومی نکنید.
در [راهنمای ساخت Docker](https://docs.liara.ir/paas/docker/how-tos/create-app/)
نوع برنامه Docker، پورت ۸۰۰۰ و منابع بالا را انتخاب کنید. شناسهٔ برنامه باید
آزاد باشد؛ نام واقعی انتخاب‌شده را در یادداشت انتشار ثبت کنید.
برای شروع Worker و Beat نخرید. در Compose نیز اکنون پشت پروفایل `background`
هستند. بسته‌های پایتونی و سابقهٔ مهاجرت آن‌ها حفظ شده‌اند.

## ۴. فضای فایل و نسخهٔ پشتیبان

یک bucket خصوصی سازگار با S3 بسازید. دسترسی عمومی کل bucket را فعال نکنید:
امضاهای خصوصی هم در همان storage ذخیره می‌شوند. تصاویر عمومی از URL امضاشده
استفاده می‌کنند. مبدأ دقیق نمایش اشیا را در CSP وارد کنید. اگر endpoint
برای امضا به region نیاز دارد، مقدار اعلام‌شدهٔ ارائه‌دهنده را وارد کنید.
نمایش عکس و پخش ویدئو با پیوند امضاشده، به‌ویژه Range و انقضای پیوند را آزمایش کنید.
فایل ویدئو حداکثر ۶۰ مگابایت است؛ تبدیل خودکار فرمت یا کیفیت انجام نمی‌شود.
برای موبایل کلیپ کوتاه MP4 با H.264/AAC تهیه کنید؛ پشتیبانی واقعی دستگاه‌ها
را پیش از استفادهٔ گسترده بررسی کنید.

هدف پیشنهادی بازیابی: حداکثر شش ساعت از دست رفتن اطلاعات و بازیابی در چهار ساعت.
این هدف هنوز اندازه‌گیری نشده است. پشتیبان PostgreSQL هر شش ساعت، نگهداری
۷ روز نسخه‌های شش‌ساعته و ۳۰ روز نسخهٔ روزانه؛ برای فایل‌ها نسخه‌بندی در صورت
پشتیبانی و یک کپی مستقل روزانه توصیه می‌شود. قابلیت و هزینهٔ این زمان‌بندی
باید در پلن پشتیبان تأیید شود؛ برنامهٔ زمان‌بندی در این کار فعال نشده است.
[راهنمای PostgreSQL لیارا](https://docs.liara.ir/dbaas/postgresql/how-tos/create-backup/)
پشتیبان خودکار روزانه و ساخت دستی از منوی پشتیبان‌گیری را مستند کرده است؛
روزانه به‌تنهایی هدف شش‌ساعتهٔ بالا را برآورده نمی‌کند و زمان‌بندی تکمیلی لازم دارد.
یک bucket دوم در همان حساب به‌تنهایی در برابر حذف حساب یا خرابی ارائه‌دهنده کافی نیست.
کلید دسترسی کپی پشتیبان را از کلید برنامه جدا نگه دارید و رمزگذاری و نگهداری
خارج از حساب اصلی را در سرویس منتخب تنظیم کنید.

نمونهٔ پشتیبان دستی، فقط در ترمینال لینوکس محیط مدیریتی مورداعتماد با ابزار
PostgreSQL 16 و دسترسی خصوصی به دیتابیس؛ این ابزار داخل تصویر وب نصب نیست:

```bash
# PGHOST, PGPORT, PGDATABASE, PGUSER از اتصال دیتابیس؛ رمز در PGPASSFILE با مجوز 600.
umask 077
pg_dump --format=custom --no-owner --file=sanga-backup.dump
pg_restore --list sanga-backup.dump
```

فرمان اول باید با کد خروج صفر پایان یابد؛ فرمان دوم فهرست جدول‌ها را نشان دهد.
فایل را با ابزار سرویس پشتیبان به فضای خصوصی مستقل منتقل کنید؛ باقی‌ماندن
آن روی رایانه یا همان سرور پشتیبان نهایی محسوب نمی‌شود.
برای بازیابی، دیتابیس جدا و خالی بسازید و اتصال PG را به **همان دیتابیس آزمایشی**
تغییر دهید؛ هرگز این فرمان را با اتصال تولید آزمایش نکنید:

```bash
pg_restore --no-owner --no-acl --exit-on-error --dbname="$PGDATABASE" sanga-backup.dump
```

سپس نسخهٔ برنامهٔ متناظر و کپی فایل‌ها را به آن متصل کنید؛ ورود، محصول،
فاکتور تأییدشده، جمع دفتر و دسترسی امضا را آزمایش کنید. نتیجه و زمان بازیابی
را ثبت کنید. این تمرین قبل از انتشار و سپس ماهانه تکرار شود.

## ۵. تنظیم متغیرها

از `.env.production.example` به‌عنوان فهرست استفاده کنید و مقادیر را در پنل
متغیرهای برنامه وارد کنید؛ فایل `.env` را به GitHub نفرستید. فیلد خالیِ اتصال
باید از پنل همان سرویس پر شود. `CACHE_URL` و `REDIS_URL` را URL واقعی Redis
بگذارید؛ برای این نسخه نیازی به راه‌اندازی broker/worker نیست.
در صفحهٔ محرمانهٔ پنل یک کلید تصادفی حداقل پنجاه‌کاراکتری وارد کنید؛ برای تولید
آن در PowerShell رایانهٔ خود، با Python نصب‌شده:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(64))"
```

خروجی یک رشتهٔ بلند است؛ آن را فقط در مدیر رمز و `DJANGO_SECRET_KEY` ذخیره کنید.
تنظیمات تولید باید `SANGA_LOGIN_PHONE_ALLOWLIST` خالی، `SMS_PROVIDER=kavenegar`،
`SMS_ALLOW_UNDELIVERED=false` و `SANGA_MVP_NAVIGATION=false` داشته باشد.
هنگام آزمایش قبل از دامنه، نشانی واقعی `شناسه.liara.run` را نیز به
Allowed Hosts و مبدأ HTTPS متناظر را به CSRF اضافه کنید.
به‌جای حذف بررسی Host یا خاموش‌کردن HTTPS، نام درست را تنظیم کنید.

## ۶. شبکه و امنیت

HTTPS را در میزبان فعال کنید. میزبان باید هدرهای پروکسی را خودش تعیین کند و
امکان جعل `X-Forwarded-Proto` و IP کاربر را از اینترنت ببندد. قبل از عمومی‌کردن،
تعداد پروکسی‌ها و روش بازنویسی `X-Forwarded-For` را با مستندات/پشتیبانی میزبان
تأیید کنید؛ سپس `SANGA_TRUSTED_PROXY_COUNT` را به تعداد واقعی تغییر دهید.
مقدار صفر امن‌تر از اعتماد بی‌بررسی است، اما ممکن است مشتریان را پشت IP مشترک
محدود کند. این مورد برای OTP پرتعداد یک شرط انتشار است.
با S3، نیازی به وب‌سرور جدا برای media نیست. اگر بعدها دیسک محلی انتخاب شد،
هر دو مسیر `/media/invoice-assets/` و `/media/invoice-signatures/` باید در
پروکسی ۴۰۴ بدهند و فقط مسیرهای احراز‌شدهٔ برنامه فایل خصوصی را ارائه کنند.

حد درخواست پروکسی را با نیاز ویدئو هماهنگ کنید: مسیر بارگذاری محصول باید
یک ویدئوی حداکثر ۶۰ مگابایتی به‌علاوهٔ سربار فرم را بپذیرد، ولی مسیر برندینگ
فاکتور محدود بماند. عدد ۸ مگابایت موجود در راهنمای عمومی را برای همهٔ مسیرها
اعمال نکنید؛ این کار ویدئوها را می‌شکند. `FILE_UPLOAD_MAX_MEMORY_SIZE` فقط آستانهٔ
نوشتن فایل روی دیسک است، نه محدودیت اندازهٔ آپلود. دیسک موقت و مجوز آن را آزمایش کنید.

## ۷. اولین انتشار؛ فقط پس از اجازهٔ جداگانه

ابتدا تغییرات را از شاخهٔ کاری با Pull Request به شاخهٔ هدف ببرید؛ شش بررسی CI
باید موفق باشند. گزارش SQLite جای آزمون PostgreSQL را نمی‌گیرد. قبل از انتشار
تست واقعی Redis، تصویر Linux، PDF فارسی و بیست نشست انجام شود.

پیشنهاد شروع: تست خودکار در GitHub و انتشار دستی نسخهٔ مشخص با CLI.
اتصال مستقیم لیارا به push در مستندات آن باعث انتشار خودکار می‌شود؛ تا زمانی
که مرحلهٔ مهاجرت و بازگشت کنترل نشده، آن اتصال را فعال نکنید.
در PowerShell رایانهٔ شخصی، با Git و Node.js LTS نصب‌شده، در پوشهٔ مخزن:

```powershell
git fetch origin
git switch --detach APPROVED_COMMIT_SHA
npm install -g @liara/cli
liara login
# فرمان بعدی استقرار واقعی است؛ فقط پس از اجازه و با شناسهٔ واقعی اجرا شود.
liara deploy --platform=docker --port=8000 --app YOUR_APP_ID
```

`APPROVED_COMMIT_SHA` شناسهٔ نسخه‌ای است که CI آن موفق شده، و `YOUR_APP_ID`
شناسهٔ برنامهٔ خریداری‌شده است. خروجی باید پایان موفق ساخت و انتشار را نشان دهد.
گزینه‌ها بر اساس [راهنمای استقرار](https://docs.liara.ir/paas/docker/how-tos/deploy-app/)
هستند؛ قبل از اجرا با `liara deploy --help` نسخهٔ نصب‌شده را بررسی کنید.
Node.js فقط برای این ابزار مدیریتی است؛ محصول مرحلهٔ build فرانت‌اند ندارد.

در اولین اجرا دیتابیس خالی است. پیش از معرفی نشانی به کاربران، در ترمینال
برنامهٔ لینوکس در پنل میزبان، داخل `/app`:

```bash
python manage.py check --deploy --fail-level WARNING
python manage.py showmigrations --plan
python manage.py migrate --no-input
python manage.py createsuperuser
```

بررسی باید بدون هشدار تمام شود؛ migrate برای مهاجرت‌ها `OK` نشان دهد و
createsuperuser ساخت موفق حساب را گزارش کند. شمارهٔ واقعی مدیر را وارد کنید.
برای ورود پنل از همان شماره و پیامک استفاده کنید. `seed_demo` و شماره‌های
آزمایشی روی تولید استفاده نشوند. `/health/` فقط اتصال دیتابیس را بررسی می‌کند؛
۲۰۰ بودن آن اثبات آماده‌بودن جدول‌ها، Redis، پیامک یا PDF نیست.
در پنل مدیر پنج کسب‌وکار و اعضا را بسازید و وضعیت تأیید، ظرفیت و نقش‌ها را کنترل کنید.

## ۸. اتصال دامنه در ایران‌سرور

پس از موفقیت محیط آزمایشی، در بخش دامنه‌های برنامه `sangesfahan.com` و در صورت
استفاده `www.sangesfahan.com` را اضافه کنید. رکوردهای دقیق نمایش‌داده‌شدهٔ لیارا
را در DNS ایران‌سرور ثبت کنید؛ IP یا مقصد CNAME را حدس نزنید. ریشهٔ دامنه معمولاً
به رکورد A/ALIAS مناسب نیاز دارد؛ روش نهایی تابع دستور میزبان و امکانات DNS است.
ثبت دامنه می‌تواند در ایران‌سرور بماند. اگر میزبان تغییر nameserver خواست، ابتدا
تمام رکوردهای موجود، به‌ویژه ایمیل، را یادداشت و در DNS جدید بازسازی کنید.
رکورد IPv6 قدیمی نباید کاربران را به سرور دیگری بفرستد.
SSL دامنه را در پنل فعال کنید و انتقال www به دامنهٔ اصلی را تنظیم کنید.
در PowerShell:

```powershell
Resolve-DnsName sangesfahan.com
curl.exe -I https://sangesfahan.com/health/
curl.exe -I http://sangesfahan.com/auth/login/
```

DNS باید با مقصد اعلام‌شدهٔ میزبان یکسان باشد؛ HTTPS سلامت ۲۰۰ و درخواست HTTP
ورود باید انتقال به HTTPS بدهد. استثنای HTTP فقط `/health/` برای پروب داخلی است.

## ۹. آزمون پذیرش و مانیتورینگ

روی موبایل اندروید و iOS، RTL، بازیابی فرم خطادار، بارگذاری عکس و ویدئو، پخش،
کاتالوگ عمومی و خروجی چندصفحه‌ای فارسی بررسی شود. دو کسب‌وکار آزمایشی جدا بسازید؛
دسترسی متقابل به محصول خصوصی، قیمت B2B، فاکتور و امضا باید رد شود.
فاکتور همکار را ارسال، رد، اصلاح و تأیید کنید؛ دوباره‌فرستادن درخواست نباید
دفتر حساب یا معامله را تکرار کند. موجودی نباید خودکار کم شود.
فاکتور مشتری و همکار محلی، چک برگشتی/وصول‌شده و گزارش مانده نیز آزمایش شوند.
بازکردن URL فایل خصوصی بدون ورود باید رد شود؛ bucket خصوصی بماند.

هشدار سلامت HTTPS هر دقیقه، خطاهای ۵۰۰، نزدیک‌شدن RAM به سقف، کمبود اعتبار پیامک،
فضای فایل و دیرشدن آخرین پشتیبان را برای خودتان فعال کنید. صرف داشتن لاگ کافی نیست؛
یک هشدار آزمایشی دریافت کنید. این پایش در این کار فعال نشده است.
رسیدن OTP، تولید PDF، دسترسی S3 و Redis جدا از `/health/` آزمایش شوند.

## ۱۰. به‌روزرسانی، برگشت و خطاهای رایج

برای هر انتشار SHA نسخه، پشتیبان، تغییرات schema و نتیجهٔ smoke test را ثبت کنید.
قبل از تغییر schema، ورود درخواست‌های نوشتنی را در میزبان متوقف و کاربران را
مطلع کنید؛ یک‌بار migrate را با نسخهٔ جدید اجرا و سپس همان نسخه را منتشر کنید.
مهاجرت نباید با شروع هر پردازش وب تکرار شود. اگر migrate شکست خورد، انتشار را
ادامه ندهید و خروجی خطا را بررسی کنید؛ دیتابیس را حذف یا reset نکنید.
برگشت تصویر برنامه فقط وقتی مجاز است که schema با نسخهٔ قبلی سازگار باشد.
اگر سازگار نیست، برنامه متوقف بماند تا راه‌حل اصلاحی یا بازیابی آزموده اجرا شود؛
بازیابی تولید می‌تواند نوشته‌های بعد از پشتیبان را از بین ببرد و تصمیم مالک است.

| نشانه | بررسی |
|---|---|
| ۴۰۰ | Allowed Hosts و نام دامنهٔ پیش‌نمایش |
| ۴۰۳ روی فرم | HTTPS و CSRF origins؛ CSRF را خاموش نکنید |
| انتقال بی‌پایان | کنترل هدر X-Forwarded-Proto توسط میزبان |
| ۴۱۳ روی ویدئو | سقف مسیر آپلود در پروکسی؛ سقف فاکتور را بی‌دلیل بالا نبرید |
| عکس نمایش داده نمی‌شود | کلید S3، endpoint، CSP، ساعت سرور و امضای URL |
| پیامک نمی‌رسد | اعتبار، قالب تأییدشده و نتیجهٔ Lookup؛ حالت console را فعال نکنید |
| خروجی ۴۲۹ | سقف یک‌دقیقه‌ای یا قطع Redis؛ لاگ عمومی و اتصال Redis بررسی شود |
| خروجی PDF خطا می‌دهد | Pango، فونت، مصرف RAM و لاگ تولید سند |
| سلامت ۵۰۳ | اتصال PostgreSQL؛ با راه‌اندازی مجدد بی‌هدف درمان نشود |

پیش از خرید نهایی، قیمت و محل سرویس‌ها، ترافیک ویدئو، امکان پشتیبان شش‌ساعته،
بازیابی آزمایشی و کنترل هدرهای پروکسی را تأیید کنید. تا رفع موارد باز گزارش
ممیزی، تصمیم انتشار **No-Go** است.
