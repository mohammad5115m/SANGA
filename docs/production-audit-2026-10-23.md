## معماری و تصمیم زیرساخت

Django 5.2.17 روی Python 3.12، معماری یکپارچه با service/selector، قالب فارسی
RTL، HTMX و Alpine محلی، PostgreSQL، Gunicorn و WhiteNoise. جست‌وجو با ORM است؛
موتور جست‌وجوی جدا لازم نیست. PDF با WeasyPrint/Pango و PNG با PyMuPDF ساخته
می‌شود. پردازش سند هم‌زمان با درخواست وب است و صف پس‌زمینه ندارد.
ورود کارکنان و تأیید مشتری از دو purpose متفاوت OTP استفاده می‌کنند و
پروایدر کاوه‌نگار از Lookup و قالب تأییدشده استفاده می‌کند.

## یافته‌های اولویت‌بندی‌شده

### P0-01 — امکان اجرای Compose تولید با تنظیمات توسعه

- فایل: `docker-compose.prod.yml` و `.env.example`.
- شاهد/علت: سرویس‌های برنامه فقط `env_file: [.env]` داشتند؛ نمونهٔ `.env`
  حاوی settings توسعه و SQLite است. این مقادیر ENV تصویر را بازنویسی می‌کنند.
  در نتیجه DEBUG، OTP آزمایشی و تمام محافظ‌های production قابل دورزدنِ ناشی
  از پیکربندی بودند.
- اثر: افشای اطلاعات توسعه و اتکا به SQLite برای عملیات مالی.
- اصلاح: هر چهار نقش settings تولید و PostgreSQL را صریح تحمیل می‌کنند؛
  خود production نیز موتور غیر PostgreSQL را رد می‌کند.
- ریسک تغییر: محیطی که عمداً Compose تولید را برای توسعه استفاده می‌کرد دیگر
  شروع نمی‌شود؛ باید از تنظیمات توسعه استفاده کند.
- اعتبارسنجی: تست checker موتور؛ بررسی واقعی Compose با `.env.example` و
  smoke تصویر در CI افزوده شد. اجرای Docker محلی ممکن نبود.

### P1-01 — فعال‌سازی حساب و کسب‌وکار تعلیق‌شده از فهرست آزمایشی

- فایل: `apps/accounts/services.py` و `config/settings/production.py`.
- شاهد/علت: `_ensure_allowlisted_login_account` پیش از OTP، کاربر و عضویت را
  فعال و وضعیت کسب‌وکار، پلن و انقضا را بازنشانی می‌کند. production فهرست
  محیطی غیرخالی را رد نمی‌کرد.
- اثر: نقض تعلیق و محدودیت provision توسط مدیر در صورت کپی تنظیمات آزمایشی.
- اصلاح: شروع production با هر فهرست غیرخالی رد می‌شود؛ رفتار دمو در توسعه حفظ شد.
- ریسک: شماره‌های قبلاً مجاز در تولید باید از مسیر مدیر ساخته شوند.
- اعتبارسنجی: تست رد فهرست غیرخالی با secret معتبر؛ تست‌های موجود دمو حفظ شدند.

### P1-03 — مسیر خام امضا از حفاظت فایل‌ها جا مانده بود

- فایل: `config/urls.py`، `apps/invoicing/models.py` و `docs/deployment.md`.

### P1-04 — محدودیت تولید خروجی بین پردازش‌ها مشترک نبود

- فایل: `apps/invoicing/rendering.py` و `config/settings/production.py`.
- شاهد/علت: cache تولید تنظیم نشده و LocMem پیش‌فرض است؛ کلید نیز برای هر
  فاکتور و نوع خروجی جدا بود.
- اثر: عبور از سقف با تعویض فاکتور، فرمت یا پردازش؛ اشغال RAM/CPU وب با PDF/PNG.
- اصلاح: cache مشترک Redis، یک سهمیهٔ کل برای هر کاربر، و رد تولید سند در قطع cache.
  متن خطای اتصال که ممکن است credential داشته باشد ثبت نمی‌شود.
- ریسک: اکنون شش خروجی در دقیقه برای مجموع فاکتورها/فرمت‌های هر کاربر است؛
  قطع Redis خروجی را با پاسخ محدودیت موجود متوقف می‌کند. خواندن سایر صفحات مستقل است.
- اعتبارسنجی: تعویض فاکتور/فرمت، استقلال کاربران و شکست اتصال بدون افشای secret؛
  آزمون Redis واقعی با درخواست‌های هم‌زمان و یک پردازش جدا به CI افزوده شد.

### P1-05 — سلامت کانتینر می‌توانست وضعیت وب را نادرست گزارش کند

- فایل: `Dockerfile`، `scripts/healthcheck.py` و production settings.
- شاهد/علت: پروب curl از Host لوپ‌بک استفاده می‌کرد؛ Host تولید می‌تواند آن را
  رد کند، و با قبول لوپ‌بک نیز redirect HTTPS ممکن بود بدون رسیدن به view موفق شمرده شود.
- اثر: کانتینر سالم ناسالم شمرده می‌شود یا redirect به‌جای بررسی دیتابیس سلامت محسوب می‌شود.
- اصلاح: پروب با Host واقعی، پاسخ ۲۰۰ و JSON وضعیت ok؛ redirect شکست است.
  تنها مسیر دقیق health از redirect داخلی HTTP معاف شد.
- ریسک: health روی HTTP هم در دسترس است و فقط وضعیت کلی DB را نشان می‌دهد؛
  سایر مسیرها همچنان به HTTPS منتقل می‌شوند.
- اعتبارسنجی: health در DB سالم ۲۰۰ و در خرابی اتصال ۵۰۳؛ مسیر ورود HTTP همچنان ۳۰۱.
  اجرای کامل کانتینر در CI آماده شده است.

### P1-06 — موارد لازمِ عملیاتی هنوز تهیه/آزموده نشده‌اند

حساب میزبانی و پیامک، bucket خصوصی، کلیدها، DNS/SSL، زمان‌بندی پشتیبان،
بازیابی، هشدارها، قرارداد هدرهای پروکسی، تحویل واقعی OTP و آزمون بار وجود ندارند.
این‌ها با کدنویسی یا تست mock تأیید نمی‌شوند و مانع اعلام آمادگی تولید هستند.
راه‌حل و آزمون پذیرش هرکدام در راهنمای فارسی آمده است؛ اجرای آن‌ها پس از
اجازهٔ جداگانه و روی محیط آزمایشی انجام می‌شود.

### P2 — بهبودهای ثبت‌شده بدون بازنویسی محصول

- Worker/Beat در Compose پشت profile قرار گرفتند تا بدون task سرویس بیهوده اجرا نشود.
- `.env.*` واقعی در Git و تصویر نادیده گرفته می‌شود؛ فقط دو نمونهٔ بدون secret استثنا هستند.
- `.env.production.example` با همهٔ امکانات، S3 و کاوه‌نگار آماده شد.
- محدودیت فعلی ویدئو فقط container را تشخیص می‌دهد، نه codec یا قابل‌پخش‌بودن؛
  برای استفادهٔ زیاد، آزمون موبایل/Range و هزینهٔ ترافیک لازم است. pipeline تبدیل
  و صف PDF در این تغییر اضافه نشد؛ نیازشان تابع اندازه‌گیری است.
- راهنمای قدیمی سقف عمومی ۸MiB پروکسی را پیشنهاد می‌کند؛ این سقف برای ویدئوی
  ۶۰MB مناسب نیست. راهنمای جدید محدودیت مسیرهای محصول و برندینگ را تفکیک می‌کند.
- `AGENTS.md` و بعضی بخش‌های معماری دربارهٔ نسخه، تعداد تست‌ها، تنظیم ruff و
  سلامت Redis قدیمی بودند؛ راهنمای agent دربارهٔ نسخه، SQLite و gateها اصلاح شد.
- تست صفحه‌بندی اعلان‌ها درج‌های متوالی را الزاماً دارای زمان متفاوت فرض
  می‌کرد. در اجرای گستردهٔ Windows این تست شکست خورد؛ زمان اعلان هدف صریحاً
  قدیمی شد و کل مجموعهٔ اعلان دوباره موفق شد. این اصلاح دادهٔ تست است، نه
  تغییر ترتیب اعلان در محصول یا پنهان‌کردن خطای برنامه.

## منطق تجاری و پوشش بررسی

مسیرهای OTP، provisioning، انتخاب tenant، سیاست نمایش کالا و قیمت، صفحات عمومی،
اسناد خصوصی، تأیید نسخهٔ فاکتور و ثبت دفتر بررسی شدند. در کد مالی قفل روی
فاکتور، کنترل نسخهٔ مورد تأیید، کلیدهای idempotency و قیود یکتایی وجود دارند.
این کنترل‌ها جای اجرای تست PostgreSQL را نمی‌گیرند.
منطق مبلغ، دفتر، تأیید دوطرفه، موجودی و ثبت‌نام در اصلاحات تغییر نکرده است.
تست‌های موجود برای B2B/B2C، tenant، محصول، کاتالوگ، مشتری، فاکتور، چک، گزارش و
مهاجرت در اجرای گسترده لحاظ شدند. بازبینی بصری واقعی روی موبایل و آزمون بار
در این محیط انجام نشده؛ از تست قالب/JavaScript نتیجهٔ ظاهری روی همهٔ دستگاه‌ها استنباط نشده است.

## نتایج اعتبارسنجی

محیط محلی: Windows، Python 3.12.14، وابستگی‌های نصب‌شده از requirements همراه
constraints اصلی. نصب اولیه خطای دریافت/resolve داشت؛ پس از ارتقای pip نصب
با همان constraints موفق شد و pinهای محصول تغییر نکردند.

| بررسی اجراشده | نتیجه |
|---|---|
| `python manage.py check` | موفق، بدون issue |
| `python manage.py makemigrations --check --dry-run` | موفق؛ تغییر schema ثبت‌نشده وجود ندارد |
| `ruff check .` | موفق |
| `pip check` | موفق |
| `compileall` برای apps/config/scripts | موفق |
| `check --deploy --fail-level WARNING` | موفق با production، PostgreSQL تنظیم‌شده و credential ساختگی؛ اتصال زنده آزمایش نشده |
| migrate روی فایل SQLite تازه با نام تصادفی | تمام مهاجرت‌ها موفق؛ هیچ دیتابیس موجودی دست‌کاری نشد |
| collectstatic با settings ساخت | ۱۸۶ فایل کپی و ۹۲۶ عملیات پس‌پردازش موفق |
| اجرای گستردهٔ pytest | ۱۰۶۱ موفق، ۴ شکست، ۳۱ skip، ۱۸۱ warning؛ حدود ۴۴۵٫۵ ثانیه |
| اجرای متمرکز نهایی پس از اصلاح دادهٔ تست اعلان | ۳۷ موفق، یک skip مربوط به Redis واقعی |

سه شکست اجرای گسترده: تولید PDF قابل‌انتخاب، صفحه‌بندی فاکتور بلند و جدول کامل
اقلام PDF؛ WeasyPrint در این Windows نتوانست `libgobject-2.0-0` را بارگذاری کند.
این‌ها موفق محسوب نشده‌اند و برای تأیید خروجی باید در Linux با کتابخانه‌های
تصویر اجرا شوند. چهارمین شکست تست ترتیب اعلان بود که در بالا توضیح داده شد
و با آزمون مجموعهٔ مربوطه تأیید شد. کل suite دوباره تکرار نشد؛ تغییر بعدی
دادهٔ همان تست و checker PostgreSQL با اجرای متمرکز پوشش داده شد.

۳۰ تست هم‌زمانی به PostgreSQL نیاز دارند و یک تست cache مشترک به Redis؛ هر
۳۱ تست محلی skip شدند. Node بسته‌بندی‌شده برای تست رفتار JavaScript معرفی شد.
اخطارهای WhiteNoise عمدتاً مربوط به ساخته‌نشدن staticfiles هنگام شروع تست‌ها
بودند؛ collectstatic جداگانه موفق شد.

در CI اجرای واقعی PostgreSQL/Redis، بررسی overrideهای Compose و ساخت/اجرای
کانتینر اضافه شده است. نتیجهٔ CI باید از Pull Request خوانده شود؛ صرف وجود
job به‌عنوان تست موفق گزارش نشده است. Docker، PostgreSQL و Redis محلی در
دسترس نبودند. تحویل واقعی SMS، S3، DNS، HTTPS، بازیابی و آزمون بار اجرا نشدند.
اسکن وابستگی‌ها تا دریافت نتیجهٔ معتبر باز است؛ نتیجهٔ آن جدا تحویل می‌شود.
